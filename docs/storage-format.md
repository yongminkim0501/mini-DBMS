# minidb 저장 포맷 (format_version 2)

테이블 하나는 데이터 파일 하나(`<db_dir>/data/<table>.tbl`)에 저장되고,
스키마는 `<db_dir>/schema/<table>.json` 에 따로 둔다.
파일은 **16바이트 고정 헤더 + 가변 길이 레코드의 연속(append-only)** 이다.
모든 정수는 little-endian.

> 버전 이력: v1 은 레코드 헤더가 `length` 4바이트뿐이었다. v2 에서 CRC 두 개를 추가했다.
> v1 파일은 `unsupported storage format version 1 (expected 2)` 메시지의 `DataCorrupted` 로
> 거부하며 마이그레이션하지 않는다(v1 은 테스트에서만 쓰였다).

## 1. 바이트 레이아웃

### 파일 헤더 (16 B)

```
 0        4        6        8                               16
 +--------+--------+--------+-------------------------------+
 | magic  | version| col_cnt|        reserved (0 x 8)       |
 | "MDB1" |  u16=2 |  u16   |                               |
 +--------+--------+--------+-------------------------------+
```

| 필드 | 크기 | 설명 |
|---|---|---|
| magic | 4 | `b"MDB1"`. 다르면 `DataCorrupted` |
| format_version | u16 | 현재 2. 다르면 `DataCorrupted` |
| column_count | u16 | 스키마 전체 컬럼 수(id 포함). 스키마와 다르면 `DataCorrupted` |
| reserved | 8 | 0. 향후 확장용(읽을 때는 검사하지 않음) |

### 레코드

```
 0          4            8             12
 +----------+------------+-------------+-------+--------+-------------+-----------------------+
 | length   | body_crc   | header_crc  | flags | id i64 | null_bitmap | fields (NULL 아닌 것만) |
 |   u32    |    u32     |    u32      |  u8   |        | ceil(n/8) B |                       |
 +----------+------------+-------------+-------+--------+-------------+-----------------------+
 \____ header_crc 대상 ___/             \______________________ body (length 바이트) ___________/
 \_____________ 레코드 헤더 12 B ________/
```

- `length` : body 의 바이트 수. 레코드 전체 크기 = `12 + length`.
- `body_crc` : `zlib.crc32(body)`.
- `header_crc` : `zlib.crc32(length 4바이트 + body_crc 4바이트)`. **length 를 보호한다.**
- body:
  - `flags` : bit0 = deleted. 나머지 비트는 0 이어야 한다.
  - `id` : int64, 파일 안에서 엄격하게 증가.
  - `null_bitmap` : `n = len(data_columns)` (id 제외) 일 때 `ceil(n/8)` 바이트.
    data_columns 의 i번째 컬럼이 NULL 이면 `bitmap[i // 8]` 의 `(i % 8)`번째 비트(LSB 가 0번)가 1.
    실제 컬럼에 대응하지 않는 상위 패딩 비트는 0 이어야 한다.
  - `fields` : data_columns 순서대로, NULL 이 아닌 컬럼만.
    BIGINT 는 int64 8 B, TEXT 는 u32 바이트 길이 + UTF-8 바이트(길이는 글자 수가 아니라 바이트 수).

본문 최소 크기 = `1 + 8 + ceil(n/8)` (모든 컬럼이 NULL 인 경우).

## 2. 실제 16진수 덤프 해설

`users(id BIGINT, name TEXT, age BIGINT)` 에 `("홍길동", 30)`, `(None, 7)` 을 append 한 파일:

```
00000000  4d 44 42 31 02 00 03 00 00 00 00 00 00 00 00 00
00000010  1f 00 00 00 ab 8a c8 af 83 1f 3b f3 00 01 00 00
00000020  00 00 00 00 00 00 09 00 00 00 ed 99 8d ea b8 b8
00000030  eb 8f 99 1e 00 00 00 00 00 00 00 12 00 00 00 d0
00000040  42 99 ae b4 b6 1b 9f 00 02 00 00 00 00 00 00 00
00000050  01 07 00 00 00 00 00 00 00
```

**파일 헤더 (0x00–0x0F)**: `4d 44 42 31` = "MDB1", `02 00` = version 2, `03 00` = 컬럼 3개, 나머지 reserved.

**레코드 1 — offset 16 (0x10), `(1, '홍길동', 30)`**

| 바이트 | 값 | 의미 |
|---|---|---|
| `1f 00 00 00` | 31 | length → 레코드 전체 12 + 31 = 43 B |
| `ab 8a c8 af` | 0xafc88aab | body_crc = crc32(아래 31바이트) |
| `83 1f 3b f3` | 0xf33b1f83 | header_crc = crc32(`1f 00 00 00 ab 8a c8 af`) |
| `00` | | flags (삭제 아님) |
| `01 00 00 00 00 00 00 00` | 1 | id |
| `00` | 0b00 | null_bitmap: name, age 모두 NOT NULL |
| `09 00 00 00` | 9 | name 의 UTF-8 바이트 길이 (3글자 × 3바이트) |
| `ed 99 8d ea b8 b8 eb 8f 99` | "홍길동" | UTF-8 |
| `1e 00 00 00 00 00 00 00` | 30 | age |

검산: body = 1 + 8 + 1 + (4 + 9) + 8 = 31 ✓

**레코드 2 — offset 59 (0x3B), `(2, NULL, 7)`**

| 바이트 | 값 | 의미 |
|---|---|---|
| `12 00 00 00` | 18 | length |
| `d0 42 99 ae` | 0xae9942d0 | body_crc |
| `b4 b6 1b 9f` | 0x9f1bb6b4 | header_crc |
| `00` | | flags |
| `02 00 … 00` | 2 | id |
| `01` | 0b01 | bit0 = 1 → data_columns[0] (name) 이 NULL |
| `07 00 … 00` | 7 | age (name 은 NULL 이라 필드 영역에 아예 없음) |

검산: body = 1 + 8 + 1 + 8 = 18 ✓

같은 내용을 `python -m minidb.tools.dump users --db <db_dir>` 로 확인할 수 있다(레코드별 CRC OK/BAD 표시).

## 3. 열 때 복구 판정

열 때 헤더 뒤부터 레코드를 하나씩 검사한다. offset 위치에서 **위에서부터 순서대로** 판정한다.
열 때는 두 CRC 와 id 만 확인하고 필드 디코딩은 하지 않는다.

| # | 조건 | 판정 | 근거 |
|---|---|---|---|
| 1 | 남은 바이트 < 12 | 잘린 꼬리 | 레코드 헤더조차 다 쓰지 못하고 죽은 경우. 검증할 CRC 도 없다. |
| 2 | header_crc 불일치 | **DataCorrupted** | length 를 믿을 수 없다. 이 length 로 "본문이 모자라다"고 판단하면 정상 데이터를 꼬리로 오인해 자르게 되므로, 그 뒤는 아예 해석하지 않는다. |
| 3 | header_crc 일치, length < 본문 최소 크기 | **DataCorrupted** | CRC 가 맞으니 이 값은 실제로 쓰인 값이다. 그런데 어떤 정상 레코드도 이보다 짧을 수 없으므로 쓰는 쪽 버그나 의도적 변조다. 크래시로는 생기지 않는다. |
| 4 | header_crc 일치, 남은 바이트 < 12 + length | 잘린 꼬리 | length 는 믿을 수 있다(2번 통과). 본문을 쓰다 죽은 경우다. |
| 5 | 본문이 다 있고 body_crc 불일치 | 마지막 레코드면 잘린 꼬리, 아니면 **DataCorrupted** | 크래시 때 파일 시스템이 크기(메타데이터)만 늘리고 데이터 블록은 0 이나 쓰레기로 남길 수 있다(ext4 `data=writeback` 등). 이것은 파일 끝에서만 생긴다. 중간 레코드의 본문 손상은 크래시로 설명되지 않으므로 손상이다. |
| 6 | id ≤ 이전 레코드 id | **DataCorrupted** | CRC 는 맞는데 순서가 틀리면 쓰는 쪽 버그다. id 를 신뢰하려면 body_crc 가 먼저 통과해야 하므로 5번 뒤에 둔다. |

**순서가 중요한 이유**

- **2 → 3 → 4**: length 를 *사용하는* 판정(3, 4)은 length 가 진짜라는 것(2)이 확인된 다음에만 할 수 있다.
  4를 2보다 먼저 하면, 깨진 length 가 파일 끝을 넘을 때 "본문이 모자라다 = 잘린 꼬리"로 판정해
  **뒤의 정상 레코드를 전부 잘라 버린다.** v1 에 실제로 있던 문제다.
  3이 4보다 먼저인 이유: 터무니없이 작은 length 는 본문 데이터가 얼마나 남았는지와 관계없이 손상이다.
- **1이 맨 앞**: 12바이트가 없으면 header_crc 를 계산할 수 없다.
- **5 → 6**: id 는 body 안에 있으므로 body_crc 가 맞아야 의미가 있다.

**header_crc 가 없으면 놓치는 손상**: body_crc 만 있다면 length 가 깨졌을 때 body_crc 를 어느 범위에 대해
계산할지부터 틀린다. length 가 파일 끝을 넘으면 "본문 부족"(판정 4)으로 보여 정상 꼬리 잘림과 구별할 수 없고,
length 가 작아지면 엉뚱한 범위의 CRC 가 불일치해 손상으로는 잡지만 *어느 레코드부터* 문제인지 알 수 없다.
header_crc 는 length 자체를 독립적으로 검증해 이 구별을 가능하게 한다.

**한계**: 판정 2 때문에, 크래시로 레코드 헤더 12바이트가 통째로 0 으로 채워진 경우(파일 시스템이 크기만 늘린 경우)도
손상으로 보고 열기를 거부한다. 자동 복구보다 데이터 보존을 우선한 결정이다. 이때는 dump 도구로 위치를 확인하고
수동으로 처리한다.

## 4. 비파괴 복구 (quarantine)

잘린 꼬리를 발견하면(판정 1, 4, 5-마지막):

1. 잘라낼 바이트 `[truncate_pos, EOF)` 를 `<table>.tbl.corrupt-<YYYYmmddTHHMMSS>` 파일로 복사한다.
   시각은 로컬 시간. 같은 이름이 있으면 `-1`, `-2` … 접미사를 붙인다(`open(..., "xb")` 배타적 생성이라
   기존 파일을 덮어쓰지 않는다).
2. quarantine 파일을 `fsync` 하고, 디렉터리도 `fsync` 해서 새 파일 엔트리를 디스크에 반영한다.
3. 그다음에야 원본을 `truncate_pos` 로 truncate 하고 `fsync` 한다.
4. `RuntimeWarning` 에 잘린 위치, 바이트 수, quarantine 파일 경로를 포함한다.
   `TableFile.quarantine_path` 로도 확인할 수 있다.

1–2 단계에서 실패하면 예외가 그대로 올라가고 원본은 수정되지 않는다. 그래서 복구 과정이 데이터를 잃게 만드는
경로가 없다.

- `readonly=True`: 파일과 디렉터리를 **절대 수정하지 않는다**. quarantine 도 truncate 도 하지 않고,
  `truncate_pos` 를 논리적 파일 끝으로 삼아 그 앞까지만 읽으며, 경고는 낸다.
- **DataCorrupted 인 경우(판정 2, 3, 5-중간, 6)** 에는 파일을 전혀 건드리지 않는다. quarantine 파일도 만들지 않는다.

## 5. 읽기 경로 검증

- `read_at` 과 `scan`(`records`) 도 레코드마다 header_crc 와 body_crc 를 검증하고, 불일치면 `DataCorrupted`.
  파일을 연 뒤에 디스크에서 비트가 바뀐 경우(다른 프로세스, 매체 오류)까지 잡는다.
- `read_at` 의 "레코드 경계가 아닌 offset" 판정은 header_crc 가 먼저 한다. 임의 위치의 12바이트가 우연히
  CRC 까지 맞을 확률은 약 2⁻³² 이다. 그 뒤에도 length 범위, body_crc, flags/비트맵 패딩, 필드 길이 일치,
  id 범위를 검사한다. 범위 밖 offset 은 `ValueError`.
- dump 도구는 예외를 내지 않는 `inspect_records()` 로 레코드마다 `OK` / `BAD(header)` / `BAD(body)` 를 표시한다.
  body 만 깨진 레코드는 건너뛰고 계속 진행하지만, header 가 깨지면 그 지점에서 멈춘다.

## 6. CRC 오버헤드 트레이드오프

레코드당 **+8 바이트**(body_crc, header_crc)가 늘어난다. 100만 건 `users` 벤치마크(M-series, 단일 스레드, 3회 측정):

| 항목 | v1 | v2 | 변화 |
|---|---|---|---|
| 파일 크기 | 37.4 MB (37.4 B/행) | 45.4 MB (45.4 B/행) | +21% (정확히 행당 +8 B) |
| 적재 | ~1.05–1.13 s | ~1.44–1.48 s | 약 +35% |
| 다시 열기(복구 스캔) | ~0.27 s | ~0.76–0.78 s | 약 2.8배 |
| 전체 scan | ~1.25 s | ~1.78–1.83 s | 약 +44% |
| 랜덤 read_at | ~2.5–2.9 µs | ~3.1–3.4 µs | 약 +20% |

- 시간 증가는 CRC 연산 자체(zlib 의 C 구현, GB/s 단위)보다 **레코드당 C 함수 호출 2회와 슬라이스 생성 같은
  파이썬 수준 오버헤드**가 대부분이다. 레코드가 작을수록(여기서는 평균 33 B 본문) 비율이 커진다.
- 다시 열기가 가장 많이 늘었다. v1 의 열기는 레코드당 정수 2개만 읽었는데, v2 는 CRC 를 두 번 계산하기
  때문이다. 1천만 건이면 약 8 초가 되므로, 그 규모가 되면 "검증된 마지막 offset/id" 체크포인트를 따로 저장해
  그 뒤만 검증하는 방식을 검토한다.
- 얻는 것: (1) 중간 손상을 꼬리로 오판해 정상 데이터를 자르는 일이 없어진다. (2) 매체 오류나 외부 변조로
  조용히 틀린 값을 돌려주는 대신 명확히 실패한다. (3) 비경계 offset 판정이 확률적으로 거의 완벽해진다.
  저장 계층의 첫 번째 책임은 데이터를 잃지 않는 것이므로 이 비용을 받아들인다.

## 7. 설계 이유

### 가변 길이 + 오프셋 방식을 택한 이유

- **공간 효율**: TEXT 는 길이가 제각각이고 NULL 은 0바이트다. 고정 길이 슬롯이면 최대 길이
  (기본 1 MiB)에 맞춰야 해서 비현실적이다.
- **주소가 단순함**: 레코드 시작 offset 이 곧 레코드 주소(RID)다. append-only 라서 한 번 쓴 레코드의 offset 은
  바뀌지 않으므로, Phase 2 의 B+ 트리는 `id → offset` 만 저장하면 되고 `read_at(offset)` 은 `pread` 1~2회로 끝난다.
- **순차 scan 이 쉬움**: 레코드 헤더의 length 만 보면 다음 레코드로 건너뛸 수 있다.
- 페이지/슬롯 구조는 UPDATE/DELETE 공간 재사용이 필요해질 때 도입할 일이라 이번 범위 밖이다.

### 헤더에 레코드 수를 두지 않은 이유

- 레코드 수를 헤더에 두면 append 마다 **파일 앞쪽(헤더)과 뒤쪽(레코드) 두 곳**을 써야 한다. 둘 사이에서 크래시가
  나면 헤더와 실제 내용이 어긋나고, 어느 쪽을 믿을지 정하는 복구 로직이 필요해진다. 순수 append 쓰기도 깨진다.
- 대신 열 때 한 번 전체를 훑어 `next_id = 마지막 id + 1` 을 복원한다. 이 과정이 CRC 검증과 꼬리 복구도 겸한다.
- 진실의 원천(source of truth)이 레코드 자체 하나뿐이므로 불일치가 원천적으로 생기지 않는다.

### read-your-writes 와 읽기 메서드의 불변식

`TableFile` 은 다음 두 불변식을 지킨다(클래스 docstring 에도 명시):

- **(a)** append 계열 메서드(`append`, `append_many`)가 반환된 시점에 `_end` 이전의 모든 바이트는 OS 에 전달되어
  있다. `append_many` 는 배치 전체를 `write` 1회로 쓰고, 반환 직전에 쓰기 버퍼를 **한 번** `flush` 한다
  (fsync 는 아님). 그래서 같은 프로세스의 어떤 파일 핸들도(다른 `TableFile(readonly=True)` 인스턴스 포함)
  명시적 flush 없이 그 레코드를 읽을 수 있다.
- **(b)** `read_at` / `scan` / `records` 는 인스턴스의 어떤 속성도 변경하지 않는다. `read_at` 은 공유 fd 에
  `os.pread` 를 쓰므로 파일 위치(공유 상태)를 움직이지 않는다. `scan` 은 제너레이터마다 자기 전용 fd 를 연다.

예전(v1 초기)에는 읽기 메서드가 `_dirty` 일 때 쓰기 버퍼를 flush 했다. 그러면 읽기가 공유 상태(쓰기 버퍼,
`_dirty`)를 바꾸므로 읽기끼리도 배타 락이 필요했다. flush 책임을 append 로 옮겨 이 문제를 없앴다.
비용은 append 호출마다 `write` 시스템 콜 1회인데, 배치 적재(`append_many`)에서는 배치당 1회라 무시할 만하다.
단건 `append` 를 대량으로 반복하는 경로는 Phase 1 실행기에서 배치로 묶는다.

내구성(전원 장애 대비)은 별개 문제로, `flush(durable=True)` 가 `os.fsync` 를 호출한다.

### append_many 의 원자성

- 1단계: 모든 행을 검증·인코딩해 메모리에 bytes 로 만든다. id 는 지역 변수로 미리 할당한다.
- 2단계: 전부 통과하면 하나로 이어 붙여 write 1회 + flush 1회. 그 뒤에야 `_end`, `_next_id` 를 갱신한다.
- 검증 실패 시 1단계에서 예외가 나므로 파일, `_end`, `_next_id` 어느 것도 변하지 않는다.
- 범위: **논리적(애플리케이션 수준) 원자성**이다. 쓰기 도중 크래시가 나면 앞쪽의 온전한 레코드는 남고,
  다음 open 의 꼬리 복구가 반쯤 쓰인 마지막 레코드만 quarantine 후 잘라낸다. 크래시 원자성까지 원하면 WAL 이나
  배치 커밋 마커가 필요하다.
- write/flush 가 OSError(디스크 부족 등)로 실패하면 상태를 갱신하지 않고 인스턴스를 닫아 이후 사용을 막는다.

### 스레드 안전성: 이번 단계에서 다루지 않은 이유와 Phase 3 락 지점

이번 단계의 `TableFile` 은 **스레드 안전하지 않다**(클래스 docstring 에 명시).

- 다루지 않은 이유: 저장 포맷과 단일 스레드 정확성을 먼저 테스트로 고정하고, 동시성은 Phase 3 에서 3.14 / 3.14t
  성능 비교와 함께 측정 가능한 형태로 넣기 위해서다.
- 대비해 둔 것:
  - 모듈 수준 가변 전역 상태 없음. 모듈 상수(struct 객체, 매직 등)는 불변이고, `RecordCodec` 도 생성 후 불변이다.
    `Catalog` 의 스키마 캐시는 인스턴스 속성이다.
  - GIL 의 암묵적 원자성에 기대지 않는다. 3.14t 에는 GIL 이 없고, GIL 이 있어도 read-modify-write 는
    원자적이지 않다.
  - 위의 불변식 (b): 읽기 메서드가 인스턴스 상태를 바꾸지 않는다.
- Phase 3 에서 거는 락 (테이블당 RW 락; 코드에 `# [LOCK:read]` / `# [LOCK:write]` 로 표시):

| 메서드 | 락 | 이유 |
|---|---|---|
| `read_at` | **공유(read)** | `_end`, `_next_id` 스냅샷만 읽고 `pread` 는 위치 공유가 없다 |
| `scan` / `records` (생성 시점) | **공유(read)** | `_end` 스냅샷만 읽는다. 순회는 전용 fd 라 락 밖에서 진행해도 된다 |
| `append` / `append_many` | **배타(write)** | `_next_id` 할당 → write → flush → `_end`/`_next_id` 갱신이 하나의 임계 구역 |
| `flush` | **배타(write)** | 쓰기 핸들 사용 |
| `close` | **배타(write)** | 쓰기 핸들 flush + 닫힘 상태 전이 |
| `Catalog.get` 의 캐시 갱신 | 별도 락 | `_cache` dict 갱신 |

  불변식 (a) 덕분에, 공유 락으로 `_end` 를 읽은 시점에 그 앞의 바이트는 이미 OS 에 있다. 그래서 읽기는 쓰기
  버퍼를 볼 필요가 없고, 쓰기 락을 잡은 append 와 겹쳐도 `_end` 앞쪽만 읽으므로 안전하다.

## 8. 실행 환경 주의 (uv)

`uv run --python 3.14 ...` 는 프로젝트 `.venv` 가 이미 3.14t 로 만들어져 있으면 **그 venv 를 그대로 재사용**한다
(3.14t 도 "3.14" 요청을 만족하기 때문). GIL 빌드를 확실히 쓰려면:

```sh
uv run --python 3.14+gil pytest   # GIL 빌드
uv run --python 3.14t    pytest   # free-threaded 빌드
```

pytest 헤더에 `minidb: python 3.14.x, free-threaded build=..., GIL enabled=...` 가 출력되므로 어떤 빌드에서
돌았는지 확인할 수 있다.
