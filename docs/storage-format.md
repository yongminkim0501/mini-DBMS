# minidb 저장 포맷 (format_version 1)

테이블 하나는 데이터 파일 하나(`<db_dir>/data/<table>.tbl`)에 저장되고,
스키마는 `<db_dir>/schema/<table>.json` 에 따로 둔다.
파일은 **16바이트 고정 헤더 + 가변 길이 레코드의 연속(append-only)** 이다.
모든 정수는 little-endian.

## 1. 바이트 레이아웃

### 헤더 (16 B)

```
 0        4        6        8                               16
 +--------+--------+--------+-------------------------------+
 | magic  | version| col_cnt|        reserved (0 x 8)       |
 | "MDB1" |  u16=1 |  u16   |                               |
 +--------+--------+--------+-------------------------------+
```

| 필드 | 크기 | 설명 |
|---|---|---|
| magic | 4 | `b"MDB1"`. 다르면 `DataCorrupted` |
| format_version | u16 | 현재 1. 다르면 `DataCorrupted` |
| column_count | u16 | 스키마 전체 컬럼 수(id 포함). 스키마와 다르면 `DataCorrupted` |
| reserved | 8 | 0. 향후 확장용(읽을 때는 검사하지 않음) |

### 레코드

```
 +-----------+-------+--------+---------------+------------------------------+
 | length u32| flags | id i64 | null_bitmap   | fields (NULL 아닌 컬럼만)     |
 |           |  u8   |        | ceil(n/8) B   |                              |
 +-----------+-------+--------+---------------+------------------------------+
             \___________________ length 바이트 ____________________________/
```

- `length` : **이 필드 뒤** 본문의 바이트 수. 레코드 전체 크기는 `4 + length`.
- `flags` : bit0 = deleted. 나머지 비트는 0 이어야 한다(아니면 손상으로 간주).
- `id` : int64, 파일 안에서 엄격하게 증가.
- `null_bitmap` : `n = len(data_columns)` (id 제외) 일 때 `ceil(n/8)` 바이트.
  data_columns 의 i번째 컬럼이 NULL 이면 `bitmap[i // 8]` 의 `(i % 8)`번째 비트(LSB 가 0번)가 1.
  실제 컬럼에 대응하지 않는 상위 패딩 비트는 0 이어야 한다.
- `fields` : data_columns 순서대로, NULL 이 아닌 컬럼만.
  - BIGINT: int64 8 B
  - TEXT: u32 바이트 길이 + UTF-8 바이트 (길이는 글자 수가 아니라 바이트 수)

본문 최소 크기 = `1 + 8 + ceil(n/8)` (모든 컬럼이 NULL 인 경우).

## 2. 실제 16진수 덤프 해설

`users(id BIGINT, name TEXT, age BIGINT)` 에 `("홍길동", 30)`, `(None, 7)` 을 append 한 파일:

```
00000000  4d 44 42 31 01 00 03 00 00 00 00 00 00 00 00 00
00000010  1f 00 00 00 00 01 00 00 00 00 00 00 00 00 09 00
00000020  00 00 ed 99 8d ea b8 b8 eb 8f 99 1e 00 00 00 00
00000030  00 00 00 12 00 00 00 00 02 00 00 00 00 00 00 00
00000040  01 07 00 00 00 00 00 00 00
```

**헤더 (0x00–0x0F)**

| 바이트 | 값 | 의미 |
|---|---|---|
| `4d 44 42 31` | "MDB1" | magic |
| `01 00` | 1 | format_version |
| `03 00` | 3 | column_count (id, name, age) |
| `00 × 8` | | reserved |

**레코드 1 — offset 16 (0x10), `(1, '홍길동', 30)`**

| 바이트 | 값 | 의미 |
|---|---|---|
| `1f 00 00 00` | 31 | length → 레코드 전체 35 B |
| `00` | | flags (삭제 아님) |
| `01 00 00 00 00 00 00 00` | 1 | id |
| `00` | 0b00 | null_bitmap: name, age 모두 NOT NULL |
| `09 00 00 00` | 9 | name 의 UTF-8 바이트 길이 (3글자 × 3바이트) |
| `ed 99 8d ea b8 b8 eb 8f 99` | "홍길동" | UTF-8 |
| `1e 00 00 00 00 00 00 00` | 30 | age |

검산: 1 + 8 + 1 + (4 + 9) + 8 = 31 ✓

**레코드 2 — offset 51 (0x33), `(2, NULL, 7)`**

| 바이트 | 값 | 의미 |
|---|---|---|
| `12 00 00 00` | 18 | length |
| `00` | | flags |
| `02 00 … 00` | 2 | id |
| `01` | 0b01 | bit0 = 1 → data_columns[0] (name) 이 NULL |
| `07 00 … 00` | 7 | age (name 은 NULL 이라 필드 영역에 아예 없음) |

검산: 1 + 8 + 1 + 8 = 18 ✓

같은 내용을 `python -m minidb.tools.dump users --db <db_dir>` 로 확인할 수 있다.

## 3. 설계 이유

### 가변 길이 + 오프셋 방식을 택한 이유

- **공간 효율**: TEXT 는 길이가 제각각이고 NULL 은 0바이트다. 고정 길이 슬롯이면 최대 길이
  (기본 1 MiB)에 맞춰야 해서 비현실적이다. 100만 건 벤치마크에서 행당 평균 37.4 B.
- **주소가 단순함**: 레코드의 시작 offset 이 곧 레코드 주소(RID)다. append-only 라서 한 번 쓴
  레코드의 offset 은 절대 바뀌지 않으므로, Phase 2 의 B+ 트리는 `id → offset` 만 저장하면 되고
  `read_at(offset)` 은 `pread` 1~2회로 끝난다.
- **순차 scan 이 쉬움**: `length` 프리픽스만 보면 다음 레코드로 건너뛸 수 있다.
- 대가: offset 만으로 임의 위치가 레코드 경계인지 증명할 수 없다. `read_at` 은 length 범위,
  flags 의 미사용 비트, 비트맵 패딩 비트, 필드 길이와 length 의 정확한 일치, UTF-8 유효성,
  id 범위를 모두 검사해 경계가 아닌 offset 을 `DataCorrupted` 로 거부한다(테스트에서 모든
  비경계 offset 을 시도해 검증). 범위 밖 offset 은 `ValueError`.
- 페이지/슬롯 구조는 UPDATE/DELETE 공간 재사용이 필요해질 때 도입할 일이라 이번 범위 밖.

### 헤더에 레코드 수를 두지 않은 이유

- 레코드 수를 헤더에 두면 append 마다 **파일 앞쪽(헤더)과 뒤쪽(레코드) 두 곳**을 써야 한다.
  둘 사이에서 크래시가 나면 헤더와 실제 내용이 어긋나고, 어느 쪽을 믿을지 정하는 복구 로직이
  필요해진다. 또 앞쪽 덮어쓰기 때문에 `O_APPEND` 스타일의 순수 append 쓰기가 깨진다.
- 대신 열 때 한 번 전체를 훑어 `next_id = 마지막 id + 1` 을 복원한다. 이 과정이 손상된 꼬리
  검출과 복구도 겸한다. 100만 건(35.7 MiB) 기준 약 0.27 s.
- 진실의 원천(source of truth)이 레코드 자체 하나뿐이므로 불일치가 원천적으로 생기지 않는다.
- 행 수가 매우 커져 재오픈 시간이 문제가 되면 체크포인트(“offset X 까지 max id Y”)를 별도
  파일로 두는 방식으로 확장할 수 있다.

### 손상된 꼬리 복구

append 중 크래시가 나면 마지막 레코드가 반쯤 쓰일 수 있다. 열 때 스캔하면서

- 남은 바이트가 4 미만(length 조차 없음)이거나, length 만큼 본문이 없으면
  → **꼬리 손상**: 마지막 온전한 레코드 끝으로 truncate + `RuntimeWarning`.
- length 가 본문 최소 크기보다 작거나, id 가 증가하지 않으면
  → **중간 손상**: 자동 복구하면 데이터를 잃을 수 있으므로 `DataCorrupted` 로 중단.

주의: 중간 레코드의 length 가 비정상적으로 커서 파일 끝을 넘어가면 꼬리 손상과 구별할 수 없어
그 뒤가 잘린다(명세대로의 동작). 레코드 체크섬은 향후 format_version 2 후보.
`readonly=True`(덤프 도구) 는 truncate 하지 않고 경고만 낸다.

### read-your-writes 처리 방식

- 쓰기 핸들(`ab`, 256 KiB 버퍼)은 열어둔 채 유지해 append 마다 open/close 하지 않는다.
- 메모리상의 논리적 끝 `_end` 와 `_dirty` 플래그를 유지한다. append 가 반환하는 offset 은
  `_end` 기준이라 아직 디스크에 없어도 확정된 주소다.
- `read_at` / `scan` / `records` 는 시작할 때 `_dirty` 면 쓰기 버퍼를 **OS 로** flush 한다
  (fsync 는 아님). 같은 프로세스의 다른 fd 는 OS 페이지 캐시를 보므로 즉시 읽힌다.
- 내구성(전원 장애 대비)은 별개 문제로, `flush(durable=True)` 가 `os.fsync` 를 호출한다.
- 읽기 경로: `read_at` 은 별도 fd 에 `os.pread` (파일 위치를 공유하지 않음),
  `scan` 은 제너레이터마다 **새 fd** 를 열어 1 MiB 청크로 읽는다. 그래서 scan 도중
  read_at/append 를 호출해도 순회가 깨지지 않으며, scan 은 시작 시점의 `_end` 까지만 본다(스냅샷).

### append_many 의 원자성

- 1단계: 모든 행을 검증·인코딩해 메모리에 bytes 로 만든다. id 는 지역 변수로 가할당한다.
- 2단계: 전부 통과하면 하나로 이어 붙여 **write 1회**, 그 뒤에야 `_end`, `_next_id` 를 갱신한다.
- 검증 실패 시 1단계에서 예외가 나므로 파일, `_end`, `_next_id` 어느 것도 변하지 않는다.
- 범위: 이것은 **논리적(애플리케이션 수준) 원자성**이다. 쓰기 도중 크래시가 나면 일부 레코드만
  디스크에 남을 수 있고, 다음 open 의 꼬리 복구가 반쯤 쓰인 마지막 레코드만 잘라낸다
  (앞쪽의 온전한 레코드는 남음). 크래시 원자성까지 원하면 WAL 이나 배치 커밋 마커가 필요하다.
- write 자체가 OSError(디스크 부족 등)로 실패하면 상태를 갱신하지 않고 인스턴스를 닫아
  이후 사용을 막는다. 다시 열면 꼬리 복구가 정리한다.

### 스레드 안전성: 이번 단계에서 다루지 않은 이유와 Phase 3 락 지점

이번 단계의 `TableFile` 은 **스레드 안전하지 않다**(클래스 docstring 에 명시).

- 다루지 않은 이유: 저장 포맷과 단일 스레드 정확성을 먼저 테스트로 고정하고, 동시성은
  Phase 3 에서 3.14 / 3.14t 성능 비교와 함께 측정 가능한 형태로 넣기 위해서다. 지금 락을 넣으면
  단일 스레드 벤치마크에 락 비용이 섞이고, 어떤 단위로 잠글지(테이블/메서드/RW 락)를
  서버 구조 없이 정하게 된다.
- 대비해 둔 것:
  - 모듈 수준 가변 전역 상태 없음. 모듈 상수(struct 객체, 매직 등)는 불변이다.
    `Catalog` 의 스키마 캐시도 인스턴스 속성.
  - GIL 의 암묵적 원자성에 기대지 않는다. 3.14t 에는 GIL 이 없고, GIL 이 있어도
    `self._next_id += 1` 같은 read-modify-write 는 원자적이지 않다.
  - `read_at` 은 `pread` 를 써서 공유 파일 위치가 없다 → 읽기끼리는 락 없이 병렬 가능한 구조.
  - `scan` 은 자기 전용 fd 를 쓴다.
- Phase 3 에서 락을 걸 지점 (코드에 `# [LOCK]` 표시):
  1. `append_many` 전체: `_next_id` 읽기 → id 할당 → `write` → `_end`/`_next_id` 갱신이 하나의
     임계 구역. (쓰기 락)
  2. `_sync_reads` (쓰기 버퍼 flush 와 `_dirty` 갱신): 읽기가 쓰기 버퍼를 건드리는 유일한 지점이므로
     append 와 상호 배제 필요.
  3. `flush` / `close`: 쓰기 핸들 사용 및 닫힘 상태 전이.
  4. `read_at` 의 `_end`, `_next_id` 스냅샷 읽기: 쓰기 락 아래에서 갱신되므로 읽기 락
     (또는 갱신 순서를 보장한 뒤 스냅샷)으로 일관된 값을 얻는다.
  5. `Catalog._cache` 갱신.
  자연스러운 형태는 테이블당 RW 락: append/flush/close 는 쓰기, read_at/scan 시작은 읽기.

## 4. 실행 환경 주의 (uv)

`uv run --python 3.14 ...` 는 프로젝트 `.venv` 가 이미 3.14t 로 만들어져 있으면 **그 venv 를
그대로 재사용**한다(3.14t 도 "3.14" 요청을 만족하기 때문). GIL 빌드를 확실히 쓰려면:

```sh
uv run --python 3.14+gil pytest   # GIL 빌드
uv run --python 3.14t    pytest   # free-threaded 빌드
```

pytest 헤더에 `minidb: python 3.14.x, free-threaded build=..., GIL enabled=...` 가 출력되므로
어떤 빌드에서 돌았는지 확인할 수 있다.
