# Phase 2 리포트: id B+ 트리 인덱스

측정: `scripts/bench_index.py` (100만 건, `gen_insert_sql.py --seed 42`), macOS 15.1 arm64 (M-series 10코어), 단일 스레드.
원본 수치: `results/index_3.14.6.json` (GIL 빌드), `results/index_3.14.6t.json` (free-threaded 빌드).
이 문서의 수치는 클러스터드 범위 스캔(§1.1)을 넣은 뒤 다시 잰 값이다. 바꾸기 전 범위 스캔 수치는 §1.1 표에 함께 적었다.
B+ 트리 기본값: order 128, leaf_fill_factor 0.9, 맨 오른쪽 분할 최적화 켬.

## 1. 핵심 결과: 인덱스 사용 / 미사용

SQL 종단(파싱 → 바인딩 → 계획 → 실행 → 결과를 모두 읽을 때까지) 평균 시간.

| 쿼리 | 3.14.6 | 3.14.6t | 접근 경로 |
|---|---|---|---|
| `WHERE id = N` 인덱스 켬 (10,000회) | **0.040 ms** | **0.046 ms** | Index Scan (점) |
| `WHERE id = N` 인덱스 끔 (20회) | 1,870.4 ms | 1,930.6 ms | Seq Scan |
| `WHERE name = '...'` (20회) | 1,881.3 ms | 1,930.9 ms | Seq Scan (인덱스 없음) |
| 인덱스 켬/끔 배율 | **약 47,000배** | **약 42,000배** | |

`dict` 로는 범위 검색을 할 수 없다. 키 순서가 없어서 모든 키를 훑거나(O(n)) 정렬해야 한다.
B+ 트리는 하한 이상인 첫 키를 O(log n) 에 찾을 수 있고, 그 뒤로는 키 순서대로 읽으면 된다.

### 1.1 범위 검색: 클러스터드 범위 스캔 전/후

범위 `id >= a AND id < a+k` 평균 시간 (ms). "이전"은 행마다 `read_at`(랜덤 읽기)을 하던 방식(커밋 109e058 의 측정),
"이후"는 트리로 시작 offset 만 찾고 `scan_from` 으로 순차로 읽는 방식(`Heap Fetch: sequential`, docs/bptree.md §2.1).
끔 = `enable_indexscan = off` (Seq Scan).

| 범위 k (전체 대비) | 3.14.6 이전 켬 / 끔 | 3.14.6 이후 켬 | 3.14.6 끔 | 배율 | 3.14.6t 이전 켬 / 끔 | 3.14.6t 이후 켬 | 3.14.6t 끔 | 배율 |
|---|---|---|---|---|---|---|---|---|
| 10 (0.001%) | 0.108 / 1,960.8 | 0.126 | 1,945.5 | 15,485× | 0.114 / 2,028.4 | 0.143 | 1,954.2 | 13,684× |
| 1,000 (0.1%) | 3.167 / 1,992.2 | **2.210** | 1,966.5 | 890× | 3.204 / 1,980.5 | **2.240** | 1,962.2 | 876× |
| 100,000 (10%) | 319.0 / 1,986.4 | **235.8** | 2,023.3 | 8.6× | 317.8 / 1,991.2 | **223.9** | 2,079.0 | 9.3× |
| 500,000 (50%) | — | 1,077.8 | 2,024.5 | 1.9× | — | 1,129.9 | 2,042.4 | 1.8× |
| 900,000 (90%) | — | 2,000.5 | 2,143.7 | 1.1× | — | 1,954.1 | 2,137.2 | 1.1× |
| 1,000,000 (100%) | — | 2,173.0 | 2,173.1 | 1.0× | — | 2,245.3 | 2,185.5 | 1.0× |

**역전이 사라졌다.** 이전 방식은 행당 약 3.2 µs(랜덤 `read_at`)로 Seq Scan(행당 약 1.9~2.0 µs)보다 비싸서, 계산상 전체의
약 60% 를 넘는 범위에서 인덱스가 더 느려졌다. 이후 방식은 행당 비용이 Seq Scan 과 같아져(같은 순차 읽기 + 디코딩 경로),
읽는 행 수가 범위만큼이므로 시간이 범위 비율에 비례한다: 50% 에서 약 절반, 90% 에서 약 0.9~0.95배, 100% 에서 같다.
100% 에서의 ±3% 차이는 반복 사이 잡음 수준이다(트리 조회 한 번 + 행마다 상한 비교 하나가 더해질 뿐이다).
중간 크기 범위도 빨라졌다: 1,000건 3.2 → 2.2 ms, 10만 건 319 → 224~236 ms (약 30%).

**10건 범위는 약간 느려졌다** (0.108 → 0.126 ms, 0.114 → 0.143 ms). 레코드 10개를 `read_at` 10번(pread 10번)으로 읽던 것을
"파일 열기 + 8 KiB 읽기 + 닫기"로 바꾼 비용이다. 처음 구현은 첫 청크를 1 MiB 로 읽어 0.36 ms 까지 느려졌는데,
첫 청크를 8 KiB 에서 시작해 두 배씩 1 MiB 까지 늘리도록 바꿔 이 정도로 줄였다(전체 스캔에는 영향 없음).
더 줄이려면 작은 범위는 `read_at`, 큰 범위는 순차 읽기를 고르는 규칙을 둘 수 있지만, 차이가 20~30 µs 라 단순한 한 가지 경로를 택했다.

## 2. 해석

**점 검색 0.04 ms 의 내역**: 트리 탐색 자체는 약 1 µs(높이 3, bisect 3번)다. 나머지 약 38 µs 는 SQL 처리(렉싱·파싱·바인딩·
계획, Phase 1 측정으로 문장당 수십 µs)와 `read_at` 한 번(pread 시스템 콜 + CRC 2개 + 디코딩)이다. 즉 인덱스를 쓰면
병목이 "데이터 접근"에서 "SQL 처리 고정비"로 옮겨 간다. 인덱스를 끄면 100만 레코드를 모두 읽고 CRC 를 검증하고
디코딩해야 하므로 1.9초로, Phase 1 기준값(1.88초)과 같다.

**id 끔 ≈ name 조건**: 둘 다 Seq Scan 이고 비용은 비교 연산보다 "레코드를 읽고 디코딩하는 일"이 지배하므로 거의 같다.
과제가 요구한 "id 기준(인덱스) vs 다른 필드 기준(선형 탐색)" 비교는 0.04 ms vs 1.9 초다.

**범위가 커질수록 이득이 줄어드는 이유**: 범위 스캔도 결과 행마다 레코드를 읽고 CRC 를 검증하고 디코딩한다.
그래서 범위가 크면 읽는 양 자체가 Seq Scan 에 가까워지고, 100% 범위에서는 같아진다(§1.1). PostgreSQL 은 통계와 비용 모델로
인덱스와 Seq Scan 중 하나를 고르지만, minidb 는 규칙 기반이라 경계가 하나라도 있으면 인덱스를 쓴다(docs/execution.md §5).
클러스터드 범위 스캔 덕분에 이 규칙이 큰 범위에서도 손해를 보지 않는다.

**LIMIT 과 범위 스캔**: `id > 500000 LIMIT 5` 는 시작 위치에서 레코드 5개(와 첫 청크 8 KiB)만 읽고 멈춘다(시연에서 0.045 ms).

**두 빌드 비교**: 단일 스레드라 차이가 작다. 트리 구성·검색·범위 스캔은 오차 범위 안에서 같고, 3.14.6t 의 SQL 점 검색이
평균 약 15%(0.040 → 0.046 ms) 느린 것은 free-threaded 빌드의 참조 카운트(biased reference counting)·원자 연산 비용으로 보인다.
반대로 100만 건 적재(INSERT + 인덱스 갱신)는 3.14.6t 가 15.0초 → 14.3초로 빠르다(§3). Phase 1 과 같은 경향(살아 있는 객체가
많을 때 GC 비용 차이)이다. 3.14t 의 진짜 이점은 Phase 3 의 다중 스레드에서 측정한다.

## 3. 인덱스 구성: 벌크 로딩 vs 증분 삽입

| 항목 | 3.14.6 | 3.14.6t |
|---|---|---|
| 테이블 열기 (검증 스캔만, 인덱스 없음) | 0.774 s | 0.787 s |
| 테이블 열기 + 벌크 인덱스 (같은 스캔 한 번) | 0.998 s | 0.994 s |
| → 열기에 더해지는 인덱스 비용 | 0.225 s | 0.207 s |
| 벌크 로딩만 (이미 모은 (id, offset) 100만 쌍) | 0.182 s | 0.178 s |
| 증분 삽입 100만 건 (순차, 맨 오른쪽 최적화 켬) | 0.669 s | 0.667 s |
| 100만 건 SQL 적재 (INSERT 200문장, 인덱스 증분 갱신 + 마지막 fsync) * | 15.01 s | 14.26 s |

\* 적재 시간은 `--fresh` 로 DB 를 새로 만든 실행(커밋 109e058 의 결과 JSON 의 `initial_load`)에서 쟀다. 이후 재측정은 같은 DB 를
다시 써서 적재 항목이 없다(적재 경로는 클러스터드 범위 스캔과 무관하다).

| 트리 | 높이 | 노드 | 리프 | 평균 리프 채움률 | 메모리 (tracemalloc) |
|---|---|---|---|---|---|
| 벌크 로딩 | 3 | 8,772 | 8,696 | 0.898 | **17.3 MiB** |
| 증분 삽입 (순차) | 3 | 8,772 | 8,696 | 0.898 | 20.9 MiB |
| 참고: `dict(id → offset)` | | | | | 40.0 MiB |

- 벌크 로딩은 증분 삽입보다 **약 3.7배 빠르다**. 루트에서 내려가는 탐색, `array.insert` 의 원소 이동, 분할과 상위 전파가
  없고 배열 끝에 `append` 만 한다.
- 열 때의 인덱스 비용(0.2초)은 벌크 로딩 순수 비용(0.18초)과 거의 같다. 파일을 **한 번만** 읽으므로 추가 I/O 가 없다.
  열기 비용의 대부분(0.77초)은 원래 하던 CRC 검증 스캔이다.
- 노드 수와 채움률이 같은데 증분 트리가 3.6 MiB 더 쓰는 이유는 `array` 의 **용량 여유(over-allocation)** 다. 하나씩 삽입하며
  자란 배열은 다음 삽입을 위해 여분 공간을 잡아 두지만, 벌크 로딩과 분할의 슬라이스로 만든 배열은 딱 맞는 크기다.
- SQL 적재 시간은 Phase 1(인덱스 없음, `results/e2e_*.json`: 14.19 s / 12.78 s)보다 0.8~1.5초 늘었다. 인덱스 증분 갱신
  (약 0.67초)과 이 벤치마크만의 마지막 fsync 가 더해진 값이다. 적재 시간의 대부분은 여전히 SQL 렉싱·파싱이다.

## 4. order 비교와 기본값 선택

100만 건, 무작위 id 10만 개 점 검색, 무작위 순서 30만 건 증분 삽입 포함.

| order | 높이 | 노드 | 메모리 | 벌크 (s) GIL / t | 순차 삽입 100만 (s) GIL / t | 무작위 삽입 30만 (s) GIL / t | 검색 (µs) GIL / t |
|---|---|---|---|---|---|---|---|
| 16 | 6 | 76,534 | 34.3 MiB | 0.281 / 0.225 | 0.858 / 0.972 | 0.412 / 0.410 | 1.266 / 1.379 |
| 32 | 5 | 36,993 | 26.8 MiB | 0.193 / 0.202 | 0.758 / 0.757 | 0.349 / 0.352 | 1.165 / 1.202 |
| 64 | 4 | 17,854 | 21.4 MiB | 0.175 / 0.183 | 0.743 / 0.723 | 0.329 / 0.326 | 1.389 / 1.088 |
| **128** | **3** | **8,772** | **17.3 MiB** | **0.178 / 0.177** | **0.691 / 0.663** | **0.319 / 0.307** | **1.158 / 1.035** |
| 256 | 3 | 4,368 | 17.0 MiB | 0.166 / 0.174 | 0.655 / 0.667 | 0.319 / 0.314 | 0.945 / 1.053 |
| 512 | 3 | 2,180 | 16.1 MiB | 0.169 / 0.174 | 0.669 / 0.682 | 0.328 / 0.329 | 1.020 / 1.023 |

(같은 실험을 두 번 돌렸다. 첫 측정에서도 순위는 같았고, 검색 µs 처럼 1 µs 근처 값은 실행마다 ±20% 흔들린다.)

**기본 order = 128** 로 정했다. 근거:

1. **16 → 128 까지는 모든 지표가 좋아진다.** 높이가 6 → 3 으로 줄어 검색과 삽입이 빨라지고, 노드 수가 줄어 노드 객체
   오버헤드(노드당 `__slots__` 객체 + 배열 2개)가 줄어 메모리가 34 → 17 MiB 가 된다.
2. **128 과 256 은 측정 잡음 안에서 같다.** 높이가 둘 다 3 이고 메모리 차이는 2% 다. 검색은 빌드마다 순위가 바뀐다.
3. **512 부터는 무작위 삽입이 다시 느려진다** (3~7%, 두 번의 측정 모두). 노드 안 배열 삽입이 최대 order 개 원소를
   옮기고(memmove), 분할 때 복사하는 양도 order 에 비례하기 때문이다. 무작위 삽입 0.319 → 0.328(GIL), 0.307 → 0.329(t).
4. 128 과 256 이 같다면 **작은 쪽**을 고른다. 분할 한 번의 복사량과 덜 찬 맨 오른쪽 노드의 낭비가 order 에 비례하고,
   테스트와 디버깅에서 노드를 들여다보기도 쉽다. 128 은 채움률 0.9 에서 높이 3 으로 약 150만 건까지 담는다
   (리프 115 × 내부 팬아웃 116²). 그 이상에서 높이가 4 가 되어도 bisect 한 번(약 0.1 µs)이 더해질 뿐이다.

파이썬에서는 디스크 페이지 크기가 아니라 "노드 객체 수(메모리, 포인터 추적)"와 "노드 안 배열 연산(C 로 구현된
bisect/memmove)"의 균형으로 order 가 정해진다. C 로 구현된 배열 연산이 노드를 크게 만드는 비용을 거의 없애 주므로,
일반적인 교과서 예제(order 3~5)보다 훨씬 큰 값이 유리하다.

## 5. 순차 삽입 분할 정책 (order 128, 100만 건 순차 삽입)

| 정책 | 삽입 시간 GIL / t | 평균 리프 채움률 | 노드 | 높이 | 메모리 |
|---|---|---|---|---|---|
| 맨 오른쪽 최적화 켬 | 0.667 / 0.667 s | **0.898** | 8,772 | 3 | 20.9 MiB |
| 끔 (항상 반반) | 0.758 / 0.745 s | 0.508 | 15,624 | 4 | 21.3 MiB |

- 반반 분할은 자동 증가 키에서 왼쪽 노드가 다시는 채워지지 않아 **채움률이 51%에 고정**되고, 노드가 1.8배 많아져
  높이가 하나 더 생긴다. 최적화를 켜면 PostgreSQL 리프 fillfactor 와 같은 90% 를 유지한다.
- 삽입 시간도 10~12% 줄어든다(분할 횟수 감소, 높이 감소).
- 메모리 차이가 노드 수 차이(1.8배)보다 작은 이유는 §3 의 `array` 용량 여유 때문이다. 반반 분할은 슬라이스로 두 노드를
  딱 맞게 새로 만들지만, 최적화 쪽 왼쪽 노드는 삽입으로 자란 배열의 여유 용량을 그대로 갖고 있다. 실제 데이터 양
  (키 수 × 16바이트)은 같으므로, 채움률 차이는 메모리보다 **높이와 노드 수**(=탐색 단계, 포인터 수)로 드러난다.

## 6. 정확성 검증 요약

- 차등 테스트: 고정 시드로 무작위 SELECT 2,500개(id/age/name 조건 0~3개, `=`/`<>`/부등호, BIGINT 범위 밖 상수, 문자열 상수,
  NULL, LIMIT)를 인덱스 켬/끔으로 실행해 결과 행이 정확히 같은지 비교한다. 점 검색·범위·모순(empty)·Seq Scan 경로가 모두
  충분히 섞였는지도 확인한다. order 4 의 작은 트리로 리프 경계를 많이 만들고, 열 때 벌크 로딩된 부분과 이후 증분 삽입된
  부분이 섞이게 했다.
- 재시작 후 인덱스 = 파일, 잘린 꼬리 복구 후 인덱스 = 복구된 파일, 삭제 플래그 레코드 제외, 열 때 파일 스캔 1회.
- 클러스터드 범위 스캔: `scan_from` 경계(첫/마지막 레코드, end 경계 직전/직후, 잘못된 offset 은 read_at 과 같은 오류),
  상하한 포함 여부 10가지, 범위 스캔이 `read_at` 을 부르지 않는지, 상한을 넘은 첫 행에서 멈추는지.
- B+ 트리: order 3/4/5/16 의 분할 경계, 무작위 삽입마다 `check_invariants`, 10만 건 대조, 벌크 로딩 0~400 의 모든 크기.
